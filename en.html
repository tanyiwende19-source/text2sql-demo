Food Delivery Analytics Assistant

Business users ask questions in plain language. The system uses a large language model to write SQL, runs it against a read-only database, retries with an automatic fix when a query fails, and returns a business-ready answer with the numbers. I evaluated it on 30 questions with known answers and improved the prompts and workflow based on the failure patterns.

ArchitectureSix steps behind every question

  1. Generate SQLThe model reads the schema, metric definitions (GMV, average order value, cancellation rate) and SQL rules in the prompt, then writes one PostgreSQL query
  2. Clean SQLA code step strips code fences, stray prefixes and trailing semicolons
  3. Run read-onlyAn HTTP call to a Supabase run_sql function that only allows SELECT / WITH, blocks write keywords and multiple statements, times out after 5 seconds and returns at most 200 rows
  4. Fix on failureIf the query errors, the error message goes back to the model to rewrite the SQL, which runs once more
  5. Merge resultsUse the fixed result when the retry ran; otherwise keep the first result
  6. ExplainReturn a conclusion, a data table, a business interpretation and the SQL used, so users can verify it

CasesThree before-and-after fixes

"What is this quarter's GMV?"
Date boundary: order_time includes a time of day, so <= '2026-09-30' stops at midnight and drops every order on the last day.
v1 · wrong
GMV = 518,700.91
where status = 'completed'
  and order_time >= '2026-07-01'
  and order_time <= '2026-09-30'
v2 · correct
GMV = 526,021.34
where status = 'completed'
-- rule: half-open date ranges;
-- the table only holds this quarter
"In the new-customer coupon experiment, what is the average number of completed orders per user in the treatment and control groups?"
Experiment denominator bias: an inner join drops assigned users who never ordered, which inflates the per-user average. This is one of the most common traps in experiment analysis.
v1 · wrong
Treatment 3.43 · Control 2.95
from ab_assignments ab
join orders o on ab.user_id = o.user_id
where o.status = 'completed'
-- denominator: users who ordered
v2 · correct
Treatment 3.34 · Control 2.82
from ab_assignments a
left join orders o on a.user_id = o.user_id
  and o.status = 'completed'
-- denominator: all assigned users
"How many users placed 10 or more orders this quarter?"
Missing outer query: v1 returned 344 rows of "1", and the explanation step read only the first row, confidently answering "just 1 user".
v1 · wrong
"Only 1 user"
select count(distinct user_id)
from orders where status = 'completed'
group by user_id having count(*) >= 10
v2 · correct
344 users
select count(*) from (
  select user_id from orders
  where status = 'completed'
  group by user_id having count(*) >= 10
) t

IterationFailure types and fixes

EvaluationHow "correct" is judged

  • Data: a synthetic food delivery database with 4 tables: 2,000 users, 300 merchants, 13,657 orders (Jul–Sep 2026) and 286 A/B test assignments. Generated with a fixed random seed, so it is reproducible.
  • Questions: 30 in total (10 easy, 12 medium, 8 hard). Hard questions cover A/B test metrics, window functions, month-over-month growth and retention, plus one question the data cannot answer, to check the system does not make things up.
  • Answer key: computed by running reference SQL with duckdb on the local CSVs and cross-checked against the database.
  • Scoring: compares query results rather than SQL text, since one question can have several correct queries. Numbers allow ±0.01, column names and order are ignored, and row order is checked where the question asks for ranking.

LimitsWhat this result does not show

  • The v2 rules were written from the v1 failures and retested on the same questions, so 90% is optimistic. The next step is a held-out test set.
  • Rules can over-generalise: in one question the model applied "use a left join" where it did not belong; rounding happened to hide the effect.
  • Model output varies: "How much did GMV grow from August to September?" was right in v1 and answered as an absolute difference in v2. The question is ambiguous, and a production system should ask the user to clarify.
  • Each question ran once, and the data and schema are simpler than a real business.

Next steps: a searchable metric dictionary injected on demand, clarifying questions for ambiguous requests, and three runs per question.
