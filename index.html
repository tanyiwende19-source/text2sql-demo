架构一次提问经过的六步

  1. 生成 SQL大模型读取 Prompt 里的表结构、指标口径（GMV、客单价、取消率等）和写法规则，输出一条 PostgreSQL 查询
  2. 清洗 SQL代码节点去掉代码块标记、多余前缀和结尾分号
  3. 只读执行通过 HTTP 调用 Supabase 的 run_sql 函数：只放行 SELECT / WITH，拦截写操作和多条语句，5 秒超时，最多返回 200 行
  4. 失败则修正执行报错时，把报错信息交回大模型改写 SQL，再执行一次
  5. 合并结果修正分支有结果时优先使用，否则使用第一次的结果
  6. 业务解读输出结论、数据表、业务解读和所用 SQL，方便业务同学复核

案例三个修复前后对比

「本季度的 GMV 是多少？」
时间边界：order_time 带时分秒，<= '2026-09-30' 只取到 9 月 30 日零点，漏掉当天全部订单。
v1 · 错误
GMV = 518,700.91
where status = '已完成'
  and order_time >= '2026-07-01'
  and order_time <= '2026-09-30'
v2 · 正确
GMV = 526,021.34
where status = '已完成'
-- 规则：时间一律左闭右开，
-- 全季度数据无需时间条件
「新客满减券实验中，实验组和对照组的人均完成订单数分别是多少？」
实验分母偏差：inner join 会丢掉分组里一单未下的用户，人均值被高估。这是实验分析里最常见的统计陷阱。
v1 · 错误
实验组 3.43 · 对照组 2.95
from ab_assignments ab
join orders o on ab.user_id = o.user_id
where o.status = '已完成'
-- 分母：count(distinct o.user_id)
v2 · 正确
实验组 3.34 · 对照组 2.82
from ab_assignments a
left join orders o on a.user_id = o.user_id
  and o.status = '已完成'
-- 分母：count(distinct a.user_id)
「本季度下单 10 次及以上的用户有多少人？」
缺少外层子查询：v1 返回了 344 行「1」，解读节点只看第一行，给出「只有 1 人」这个笃定但错误的结论。
v1 · 错误
「只有 1 位用户」
select count(distinct user_id)
from orders where status = '已完成'
group by user_id having count(*) >= 10
v2 · 正确
344 人
select count(*) from (
  select user_id from orders
  where status = '已完成'
  group by user_id having count(*) >= 10
) t

迭代错因分类与改法

v1 的 9 道错题归为 5 类，每类对应一个改动。其中一类不是模型的问题，而是我自己工作流里的 bug。

错误类型原因改动结果
时间边界用 <= 月末日期，漏掉最后一天Prompt 规定左闭右开修好
实验分母inner join 丢掉零订单用户从分组表出发 left join，状态写进 on 条件修好
工作流 bug修正分支执行了，但变量聚合器总取第一个有值的变量，修正结果被丢弃对调聚合器变量顺序修好
SQL 结构缺子查询、HAVING 引用别名、别名未定义补充子查询、窗口函数、留存写法规则和别名自检部分修好
输出与解读月份输出成日期；解读只看第一行规定数字月份；解读必须基于全部行修好

评测怎么判断「答对了」

  • 数据：模拟外卖业务库，4 张表：用户 2,000、商家 300、订单 13,657（2026 年 7–9 月）、A/B 实验分组 286；固定随机种子，可复现。
  • 题目：30 题，简单 10、中等 12、困难 8；困难题覆盖 A/B 实验指标、窗口函数、环比、留存，另有 1 道「数据里没有」的题，检验系统会不会编答案。
  • 标准答案：用 duckdb 在本地 CSV 上执行标准 SQL 得出，与数据库结果交叉核对。
  • 判分：比较查询结果而不是 SQL 文本（同一问题有多种正确写法）；数值允许 ±0.01，列名和列顺序不限，有排序要求的题检查顺序。

局限这个结果的边界

  • v2 的规则是对照 v1 错题写的，并在同一套题上复测，90% 偏乐观；下一步应留出独立测试题做最终评测。
  • 规则会被过度泛化：有一题模型把「用 left join」用到了不该用的地方，四舍五入后数值碰巧没变。
  • 模型有随机性：「9 月 GMV 环比增长了多少」v1 答对、v2 答成了金额差，题目本身也有歧义，生产中应先向用户确认。
  • 每题只跑一次，数据和表结构比真实业务简单。

下一步：把指标口径做成可检索的指标字典按需注入；对有歧义的问题先追问；每题重复 3 次取平均。
